# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Desktop (Wayland/Hyprland) half of a "vehicle motion cues" tool: a particle-style dot generator drawn as a click-through overlay. The phone sender is a separate project in `../AmsDotsMobileController`. `README.md` documents the dot behaviour, the config keys and the Wayland concepts mapped to code.

## Commands
- `cargo run` (follows the phone over Bluetooth), `cargo run -- --no-phone` (at rest or set by hand) or `cargo run -- tests/data/drive.csv` (replay) — overlay on every monitor (needs a live Wayland session with wlr-layer-shell). It **starts in the background and returns the terminal** (log: `~/.local/state/ams-dots/ams-dots.log`); add `--foreground` to keep it in the terminal (Ctrl+C stops) when debugging. `ams-dots-linux stop` / `restart [options]` / `reload` (re-read the config). `--config FILE` overrides `~/.config/ams-dots/config.toml`.
- Manual control without the phone: `ams-dots-linux move DIR [SPEED]` / `speed N|+N|-N` / `direction D|+D|-D` / `auto` (`manual.rs`; DIR = up/down/left/right/diagonals or degrees clockwise from the top, SPEED = % of `motion.max_speed`).
- `--record FILE` writes every received sample (raw phone values and the fused forward/lateral/yaw) as CSV (`motion::RECORDING_HEADER`); the first thing to ask for when the dots misbehave on a drive
- `cargo test` — all unit tests; `cargo test spring` or `cargo test dots_flow_with_the_felt_inertia` runs a subset by name
- `ams-dots-linux status [--watch]` / `phones` / `select [N|NAME|any]` / `forget` / `connect` / `disconnect` / `relearn` — talk to the running overlay via `$XDG_RUNTIME_DIR/ams-dots.sock`; `--pick` forces the start-up phone list
- `hyprctl layers` — verify the `ams-dots` surface is on the overlay level

- Testing the overlay on the dev machine while the user may run their own: give the binary a private `XDG_RUNTIME_DIR` containing only a symlink to the real `wayland-1` socket, plus private `XDG_STATE_HOME`/`XDG_CONFIG_HOME` (control socket, phone memory, log and config are then separate). The session is often locked: the lock screen covers the overlay, so screenshots (`grim`) do not show the dots; check through `status`/the log instead.

## Architecture
Per frame: `MotionSource::at` (phone or replay sample; zeros without a phone), or `Manual::sample` when set by hand, `Spring` smooths (lateral, forward) acceleration -> intensity + drift -> `particles::Field` -> `Vec<Dot>` -> `dots::draw` into a `Pixmap` -> `wl_shm` buffer.
- `particles.rs`, `spring.rs`, `dots.rs`, `config.rs`, `replay.rs`, `protocol.rs`, `fusion.rs`, `speed.rs`, `motion.rs`, `manual.rs`, `cli.rs` are Wayland- and Bluetooth-free and unit-tested; keep Wayland code in `overlay.rs`.
- `overlay.rs` holds all Wayland state in one `App`, driven by sctk handler traits; each monitor has its own `Overlay` with its own `Sim` (field + spring). Draw only after the compositor's `configure`; request the next frame callback *before* the commit it belongs to, or the animation stalls. `frame_pending` prevents duplicate callback chains.
- Service model: `main::start` asks any picker question on the terminal, then `service::launch` re-runs the binary with `--foreground` in a new session (`setsid`, stdout/stderr to the log) and waits until the control socket answers. `overlay::run(.., ready)` calls `ready` after the compositor connection works and *that* is where the control server (`control::spawn`, own thread, any mode), the signal handler and the Bluetooth thread start, so a start that cannot work never looks like a running service. `control::is_running` (a connect to the socket) is the single-instance check; a stale socket file does not count. `service::shutdown` (from `stop` or SIGINT/SIGTERM) disconnects the phone, removes the socket and exits. `--no-phone` starts the Bluetooth thread *disabled* (`Live::set_enabled(false)`), so `connect` works later; only replay mode has no Bluetooth thread (`Context::phone == false`).
- Everything that used to need a restart goes through shared state polled once per frame by the overlay: `manual::Manual` (direction/speed) and `config::Settings` (`reload`; the overlay compares `generation()` in `App::draw` and restarts every `Sim`). A rejected reload keeps the old settings. New control commands go in `control::handle_command` (tested via `Context`), not in the overlay.
- Click-through relies on the empty input region set in `App::add_overlay`; do not remove it.
- Dots are painted directly into the `wl_shm` buffer (`PixmapMut::from_bytes`) with no R/B swap, which is only valid while dots are white/black (see `App::draw`).
- Performance depends on partial clearing: `App::slots` records what each reused buffer holds and `draw` clears only those rectangles. Changing how or where dots are painted (e.g. adding glow or new bands) must keep `dots::bounds_by_side` covering every painted pixel, or ghost dots remain on screen.
- Sign conventions: `forward > 0` = speeding up (dots flow down), `lateral > 0` = passengers pushed right (dots flow right); `fusion.rs` produces the same conventions from phone data (up = gravity, which Android reports pointing up; right = forward x up; lateral = minus the acceleration along right; yaw = gyro . up). Forward is learned automatically (principal axis of straight-driving acceleration after >5 s, front/back from turns: acceleration x yaw points left); its tests drive the bundled `drive.csv` through random phone orientations. There is deliberately no manual calibration.
- GPS speed: protocol v2 carries the phone's newest GPS fix (speed cm/s, and its age against the packet's first sample) in the header; v1 packets still decode, with no speed. `Live::push` hands it to `speed::SpeedAid`, which corrects only `forward` (observer: integrate forward into a speed estimate, compare each *new* fix, recognised by its fix time, with the estimate at that time, feed the error into the estimate and an acceleration bias). The GPS value is never used alone because it is ~1 s late and 1 Hz. No fix for 3 s, a reconnect or `relearn` drop it and the accelerometer alone drives the dots. Tuning constants and rationale are at the top of `speed.rs`.
- sctk 0.21 uses `delegate_dispatch2!` (not the older per-protocol `delegate_*` macros).
- New config keys: add to the struct, `Default`, `validate`, `config.example.toml` (a test checks the example matches the defaults) and the README table.
- Phone link: `picker::startup` decides at start: `--phone` wins, `--pick` asks, otherwise the remembered phone (`~/.local/state/ams-dots/phone`, trait `PhoneMemory`) connects with no question, and only with nothing remembered is the list shown (scan in `ble::scan`) or, without a terminal, the first phone taken. The receiver stores whichever phone connects (`ble::spawn(.., remember)`). The phone to follow lives in `Live::target` (with a generation counter): `select` changes it, `ble::until_changed` ends the session and the loop reconnects; `find_phone` reports sightings to `Live` for `phones`. Phones are matched by Bluetooth *name* because the phone's random address changes with every advertising session. `ble.rs` runs a tokio current-thread runtime on its own thread (the Wayland loop is blocking and sync). The only shared state is `motion::Live` behind a mutex; data older than `STALE_AFTER` or a disconnect reads as zero motion so the dots settle. The phone advertises no name, so it is found by service UUID. `protocol.rs` must keep passing `../AmsDotsMobileController/protocol/vectors.txt` (included at compile time by its tests).
- BlueZ 5.87 on the dev machine segfaults when discovery is filtered by service UUID (`DiscoveryFilter::uuids`) and a matching device shows up, and when `Adapter::remove_device` is used on cached devices. Never use either: set no UUID filter and match `device.uuids()` yourself (see `ble::open_adapter`). A killed process leaves its BLE connection open in BlueZ (the phone then stops advertising), hence `service::shutdown_on_signals` and accepting already-connected phones in `fresh_phones`.
- Testing against the real phone: `adb` is at `~/Android/Sdk/platform-tools`; the app's Start button is at about (540, 1226) on the 1080x2400 screen when stopped (the layout moves while running); `adb logcat -s AmsDots` shows connection, MTU, subscription and the sensor rate every 5 s. The picker needs a terminal: drive it through a pty (Python `pty`), not a pipe.
